# 流式 Markdown 渲染：从 O(n²) 到 O(n)

> 本文记录 RAG 知识库问答项目里的一次性能优化：把「边生成边渲染 Markdown」的主线程开销，从随回答长度平方增长降到线性增长。

## 一、问题：回答越长，页面越卡

接入流式输出后，打字机效果很爽，但长回答会肉眼可见地变卡：前面几个字还流畅，到二三百字时开始掉帧，滚动都跟不上，风扇也开始转。

直觉上流式渲染的总开销应该和回答长度成正比——毕竟只多显示几个字。但实际不是。

## 二、定位：每个 token 都在全量重解析

渲染层原来长这样（简化）：

```tsx
// 每来一个 delta，content 变化，整个组件重渲染
<ReactMarkdown remarkPlugins={[remarkGfm]} rehypePlugins={[rehypeHighlight]}>
  {content}
</ReactMarkdown>
```

关键在于 `ReactMarkdown` 是无状态的纯函数组件：**它只会「把这一整段文本重新解析成 AST，再渲染成 React 元素」**，没有增量更新的概念。

于是第 k 个 token 到达时，要对前 k 个字符做一次完整解析。设总长度 n，总开销是

```
1 + 2 + 3 + ... + n  ≈  n² / 2
```

再叠加两件事：

1. `remark-gfm` 要重新解析表格、任务列表等语法节点
2. `rehype-highlight` 会对**每个**代码块重新做语法高亮

回答里带一个 50 行的代码块时，这步尤其贵——而它每个 token 都在重复做。

用 React DevTools Profiler 能看到每次 commit 里 `ReactMarkdown` + `hast` 相关节点占了绝大部分时间，且单次耗时随内容长度线性上升——整体就是平方级。

## 三、方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
| 节流渲染 | 每 100ms 才更新一次 | 治标。渲染次数少了，但每次仍是全量解析，长回答依旧卡；调大间隔又会让打字效果变得一顿一顿 |
| 虚拟滚动 | 只渲染可视区域 | 回答本身是不断增长的单一文档，切分意义不大，实现成本高 |
| 增量分块 | 已完成的部分冻结，只重算最后一段 | ✅ 采用。改动小、收益直接、退化路径清晰 |

核心洞察：**流式输出天然有「已完成」和「进行中」的边界**。Markdown 的语义块以空行分隔，一旦某个块后面出现了新的空行，它就不会再变了——这部分可以完全冻结。

## 四、实现：分块 + memo + 纯文本尾巴

### 1. 切块

```ts
const blocks = content.split(/\n\n+/);
```

### 2. 已完成的块交给 memo 组件

```tsx
const StableBlock = memo(function StableBlock({ text }: { text: string }) {
  return (
    <ReactMarkdown remarkPlugins={[remarkGfm]} rehypePlugins={[rehypeHighlight]}>
      {text}
    </ReactMarkdown>
  );
});
```

`text` 不变 → memo 直接跳过重渲染 → 这个块**永远只解析一次**。

### 3. 最后一块用纯文本

还没结束的块随时会被追加，不适合做 Markdown 解析（半截的 `**`、未闭合的代码块都会解析错）。直接渲染纯文本：

```tsx
<div className="whitespace-pre-wrap leading-relaxed">{tail}</div>
```

代价是流式过程中最后一段没有样式（比如粗体、代码高亮），但它本来就只存在几百毫秒。

### 4. 结束后全量渲染一次

流式完成时 `streaming` 变 `false`，走完整 Markdown 渲染路径，最终结果与「一次性解析全文」完全一致——**优化不影响最终的正确性**，这是它最让人放心的点。

于是每次 token 到达时，真正需要做的事只有：重新渲染最后一段纯文本。总开销从 O(n²) 降到 O(n)。

## 五、踩过的坑

### 坑 1：直接在 `\n\n` 上切会把代码块切断

代码块里经常有空行：

````markdown
```js
const a = 1;

const b = 2;
```
````

按空行硬切会把这段代码劈成两块，各自渲染——第一块变成「未闭合的代码块」，第二块变成普通段落，视觉上完全乱掉。

修法是写一个 **fence 感知**的分割器：扫描每一行，遇到 ``` / ~~~ 切换「是否在代码块内」的状态，只有不在代码块里时，空行才是分块点。同时要处理未闭合的情况（流式过程中代码块刚开始，还没有结束标记），此时整段保持为一个块。

```ts
// lib/markdown-blocks.ts （节选）
if (fence) {
  if (fenceMarker === null) fenceMarker = marker;      // 进入
  else if (marker === fenceMarker) fenceMarker = null; // 闭合
  current.push(line);
  continue;
}
if (fenceMarker === null && line.trim() === "") flush(); // 只有块外空行才切
```

这个函数我单独抽到了 `lib/markdown-blocks.ts`，配了 7 个单元测试（覆盖多空行、`~~~`、未闭合、空字符串等情况）——纯函数好测，也比在组件里调试便宜得多。

### 坑 2：key 必须稳定

```tsx
{blocks.map((block, i) =>
  i < lastIdx ? <StableBlock key={`b-${i}`} text={block} /> : <div key="tail">…</div>
)}
```

按索引做 key 在这里是安全的：块一旦完成就不会再变，只会在尾部追加新块，索引与内容一一对应。如果按内容 hash 做 key，反而会因为重复段落导致 key 冲突。

### 坑 3：表格跨块

Markdown 表格行之间没有空行，空行出现即表格结束，所以表格不会被切开。真正会跨块的结构是 HTML 标签或引用块的松散写法，这类内容在流式期间会短暂显示为纯文本，结束后恢复正常——可以接受。

## 六、效果

- 每个 token 触发的高亮/AST 解析从「全文」降到「最后一段」，主线程耗时随长度线性增长
- 本项目实测：一段 1500 字、带代码块的回答，首屏可交互时间从约 5 秒降到 1 秒以内；连续输出时不再掉帧
- 最终渲染结果与优化前逐字节一致（流式结束后全量渲染兜底）

## 七、什么场景适用

这套方案适合「**单个持续增长的长文本**」的流式渲染。如果是一个多轮消息列表，优化重点会变成消息级别的 memo 和滚动策略；如果是短回答（一两百字），收益有限，直接全量渲染更省事。

判断标准很简单：**看 profiler 里单次渲染耗时是否随内容长度上升**。如果是，就说明有 O(n²) 等着你。
